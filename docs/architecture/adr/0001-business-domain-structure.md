# ADR-0001：按稳定业务能力组织源码

- 状态：Accepted
- 日期：2026-07-30
- 决策范围：仓库目录治理

## 背景

项目由多人迭代，后端同时存在传统横向目录和新的业务域目录，前端则在
`pages`、`api`、`components` 与图谱目录之间分散。仅按技术类型查找会迫使
开发者跨多个目录搜索同一个功能。

## 决策

1. 保留 `backend/`、`frontend/` 作为稳定部署边界。
2. 后端以现有 `ontologies`、`data_channel`、`api_hub` 等业务域作为优先实现
   位置；迁移台账中的旧目录实现仍是当前事实。
3. 前端逐步迁移到 `src/app/`、`src/features/`、`src/shared/` 三层，feature
   名与稳定导航能力对应。单个业务域必须先提交迁移 ADR 并建立骨架，才能
   切换其新增代码位置。
4. 导航作为发现地图，不要求每个页面或 Tab 拥有独立后端包。
5. 鉴权、收件箱、基础设施等横切能力允许独立于导航存在。
6. 旧横向目录以有期限的兼容 facade 为主；除例外实现的必要修复外，禁止
   新增业务实现。

## 结果

- 新同事可从导航定位到前后端代码和测试；
- 业务规则拥有单一 canonical import；
- 不会因界面改名而被迫迁移领域模型；
- 迁移需要临时维护兼容 facade 和边界检查。

## 被否决方案

- 一次性把所有源码移动到 `apps/`：部署耦合高，发现性收益有限。
- 后端严格一一对应每个前端页面：会复制模型并制造跨页面反向依赖。
- 立即删除旧横向目录：现有测试、patch、任务和迁移仍依赖旧路径。
